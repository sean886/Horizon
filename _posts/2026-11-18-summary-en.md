### [Java4Shell RCE in OpenJDK Base64 Processing Affects Java 17, 21, 25, 27](https://calif.io/java4shell/) ⭐️ 8.0/10

A technical writeup and Hacker News discussion describe CVE-2026-114938, dubbed Java4Shell, as an unauthenticated remote code execution flaw in OpenJDK triggered during Base64 processing, with a CVSS 4.0 score of 9.2 and a reported nearly four-year period of latency before disclosure. The affected versions are listed as Java 17 from 17.0.6 onward, plus Java 21, 25, and 27; standard Java 8 and 11 are generally unaffected, except for Oracle Java 8 Performance Pack. The flaw is said to affect only x86-64 servers with AVX-512 VBMI, roughly Intel Ice Lake and newer Xeon processors from 2021 onward and AMD Zen 4 and newer EPYC/Ryzen processors from 2022 onward; ARM64 is unaffected.

hackernews · werrett · Nov 17, 21:11 · [Discussion](https://news.ycombinator.com/item?id=50538240)

**「Background」** The vulnerable path runs through HotSpot, OpenJDK&\#x27;s default virtual machine, whose C2 JIT compiler emits a specialized SIMD Base64 decoding stub when the underlying CPU supports AVX-512 VBMI instructions. Because that stub is generated by HotSpot&\#x27;s JIT rather than by shared Java library code, the exposure is limited to HotSpot-based runtimes—OpenJDK, Oracle JDK and GraalVM—while JVMs such as OpenJ9 and Zing that replace or omit C2 fall outside the reported scope. The affected code is reported to have entered the 17.0.6 line and to have gone unnoticed for roughly four years, which is why Java 17, 21, 25 and 27 appear in early advisories but standard Java 8 and 11 builds generally do not.

**「Exposure and mitigation」** Operators run Java 17 through 27 on AVX-512-capable x86-64 hosts — roughly Ice Lake-era Intel Xeon and Zen 4-era AMD parts — should treat internet-reachable Base64-processing endpoints as the exposure set, since the described attack path was carried out over public IPs and is sensitive to RTT and jitter. Commenters point to Semgrep&\#x27;s free detection scripts, which test five conditions and exclude non-HotSpot VMs such as OpenJ9, GCJ and Azul Prime \(Zing\); the suggested -XX:UseAVX=2 JVM flag workaround is described in the thread as unconfirmed. Fixed builds plus WAF and Sigma detection rules are reported as available for CVE-2026-114938.

**「Community discussion」** Commenter ievans said Semgrep published free detection scripts for CVE-2026-114938 covering five conditions, including a HotSpot-based VM requirement that covers OpenJDK, Oracle JDK, and GraalVM JDK, while OpenJ9 and GCJ are not affected. Another commenter cited an unconfirmed Twitter claim that the bug lies in AVX-512 Base64 decoding and can be worked around with -XX:UseAVX=2, while the writeup&\#x27;s remote heap-grooming section, quoted in comments, says the attack is sensitive to RTT and jitter and favors low, stable latency.

### [Datasette Lite rewritten to run full Datasette in the browser](https://simonwillison.net/2026/Nov/17/datasette-lite/) ⭐️ 8.0/10

Simon Willison released a complete rewrite of Datasette Lite that uses service workers and Pyodide to run the full Datasette Python application in the browser, which he says is now almost indistinguishable from the server-side version. Through crafted lite.datasette.io URLs, users can load SQLite databases, JSON, CSV or SQL files; choose a released Datasette version from PyPI or a commit, tag or branch from GitHub; select among more than 100 SQLite versions; and install Datasette plugins from PyPI or wheel URLs, including JavaScript visualization tools. Loaded database and metadata URLs must have open CORS headers.

rss · Simon Willison · Nov 17, 16:48

**「Earlier Datasette Lite」** Datasette Lite first launched in 2022 as a proof-of-concept that ran Datasette inside a Pyodide web worker and injected the resulting HTML into the page with innerHTML. That approach broke features relying on JavaScript, because script tags inserted via innerHTML do not execute, and it struggled to load additional JavaScript resources. The rewrite replaces that simulation with service workers so the browser can run the fuller Datasette application.

**「Impact」** Datasette maintainers and plugin authors can publish URL-addressable demos and bug reproductions that pin a Datasette ref, SQLite version and plugins without hosting a server; Willison has already linked such URLs in a pagination bug report. Anyone loading a remote database or metadata file must host it with open CORS headers, or those loads will be blocked.

### [External sandbox pattern for coding agents, with three server implementations](https://simonwillison.net/2026/Nov/17/external-sandboxes-for-coding-agents/) ⭐️ 7.0/10

Simon Willison and AI research lab Prime Radiant published an &quot;external sandbox&quot; pattern for coding agents, in which the agent itself runs outside a dedicated sandbox and sends every code-execution request into it. They released three implementations that expose the same localhost API: external-sandbox-v86 \(a Node.js server running Alpine Linux under v86 in WebAssembly\), external-sandbox-container \(a Python web server using an Apple Containers instance\), and external-sandbox-quicksand \(a Python web server built on Microsoft&\#x27;s Quicksand, which bundles QEMU and Alpine Linux in a Python package\). Because the API is uniform, tools such as Pi, Claude Code, and Codex can be configured to route their code execution to whichever sandbox is running.
